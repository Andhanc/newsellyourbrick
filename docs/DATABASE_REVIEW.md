# Аудит базы данных: недостатки и рекомендации по улучшению

Документ описывает выявленные недостатки схемы и использования БД (SQLite, better-sqlite3) и предлагает меры для ускорения ответов, уменьшения лишних запросов и повышения стабильности.

---

## 1. Лишние / дублирующие таблицы

### 1.1 Три таблицы недвижимости (properties, properties_apartments, properties_houses)

**Проблема:** Одновременно используются:
- `properties` — старая единая таблица (из init.sql);
- `properties_apartments` — квартиры и коммерческая недвижимость;
- `properties_houses` — дома и виллы.

Код при каждом обращении по `property_id` вынужден проверять три таблицы подряд (см. server.js: 9126–9155, 6924–6950, 8738–8764 и др.). Это даёт до **3 запросов на один объект** и усложняет логику.

**Рекомендации:**
- **Вариант A (минимальные изменения):** Оставить три таблицы, но добавить в `bids` и везде, где хранится ссылка на объект, колонку `property_table` (`'properties' | 'properties_apartments' | 'properties_houses'`). Тогда для каждой ставки/запроса — один целевой запрос вместо трёх.
- **Вариант B (долгосрочно):** Перейти на одну таблицу `properties` с полем `property_type` (`apartment`, `house`, `villa`, `commercial`) и общими/опциональными полями. Различия по типам хранить в JSON или в отдельных колонках с NULL. Это уберёт дублирование схемы и все тройные проверки.

### 1.2 users и whatsapp_users

**Проблема:** Есть и `users` (в т.ч. с `phone_number`), и отдельная таблица `whatsapp_users` с похожими полями (phone_number, first_name, last_name, country и т.д.). Возможна рассинхронизация и дублирование данных.

**Рекомендации:**
- Либо хранить WhatsApp-данные в `users` (доп. поля или JSON), а `whatsapp_users` убрать.
- Либо явно разделить: `users` — только залогиненные пользователи приложения, `whatsapp_users` — только контакты/лиды из WhatsApp, с ссылкой `user_id` на `users` при привязке. Тогда не дублировать одни и те же сущности в двух таблицах.

## 2. Лишние запросы и N+1

### 2.1 Список ставок пользователя: 3 запроса на каждую ставку

**Где:** `server.js` ~9122–9193 (GET ставок по userId).

**Проблема:** Для каждой ставки выполняется до трёх запросов (apartments → houses → properties), чтобы найти объект. При 50 ставках — до 150 дополнительных запросов.

**Рекомендации:**
- Добавить в таблицу `bids` колонку `property_table` и при создании ставки записывать, из какой таблицы объект. При выборке ставок делать один запрос к нужной таблице по `(property_id, property_table)` или один batch: сгруппировать по `property_table` и выбирать объекты пачками через `IN (...)`.
- Либо загружать все нужные property_id по таблицам одним запросом (например, все id из apartments, потом из houses, потом из properties), собрать Map(propertyId -> property) и подставлять в ответ — без запросов в цикле.

### 2.2 Повторяющиеся проверки существования таблиц и PRAGMA

**Проблема:** В разных местах при одном и том же запросе вызываются:
- `SELECT name FROM sqlite_master WHERE type='table' AND name='...'`;
- `PRAGMA table_info(properties_apartments)` и `PRAGMA table_info(properties_houses)`.

Например, при запросе списка объявлений с тест-таймерами (server.js ~6710–6728) и при модерации (~6444–6445) структура проверяется заново. Это лишние обращения к системным таблицам при каждом запросе.

**Рекомендации:**
- Проверять наличие таблиц и (при необходимости) структуру один раз при старте приложения и кэшировать результат в памяти.
- В рантайме не вызывать `PRAGMA table_info` для каждого запроса.

### 2.3 Дублирование кода создания таблицы auction_winners

**Проблема:** Логика «если таблицы нет — создать auction_winners» повторена в трёх местах: server.js ~357–392, ~9266–9299, ~9399–9429. При изменении схемы легко забыть обновить все вхождения.

**Рекомендации:**
- Вынести создание таблицы `auction_winners` в один модуль (например, в `database.js` вместе с остальными таблицами) и вызывать его при инициализации БД. В server.js только использовать таблицу, не создавать её.

## 3. Схема и целостность данных

### 3.1 bids.property_id без привязки к таблице

**Проблема:** В `add_bids_table.sql` указан `FOREIGN KEY (property_id) REFERENCES properties(id)`, но объекты могут лежать в `properties_apartments` или `properties_houses`. В комментарии в server.js (~8682, 8905) даже указано, что FK на property не используется. В результате:
- Нет ссылочной целостности для объектов в apartments/houses.
- Невозможно понять по одной записи bids, откуда подгружать объект — отсюда три запроса подряд.

**Рекомендации:**
- Добавить в `bids` колонку `property_table` и убрать FK на `properties(id)` (или не создавать его, если объекты могут быть в разных таблицах). При добавлении ставки всегда сохранять таблицу-источник.
- Либо (при переходе на одну таблицу properties) оставить один FK на `properties(id)`.

### 3.2 purchase_requests: сильная денормализация

**Проблема:** В `purchase_requests` скопировано множество полей объекта недвижимости (property_title, property_description, property_price, property_rooms, property_bathrooms и т.д. — десятки колонок). Это:
- Дублирование данных и риск расхождения с объектом при изменении.
- Раздутая таблица и лишний трафик при выборке списка заявок (если не все поля нужны).
- Сложность поддержки: каждое новое поле объекта приходится дублировать в purchase_requests.

**Рекомендации:**
- Оставить в `purchase_requests` только ссылки: `property_id` + `property_table` (или один `property_id` при одной таблице недвижимости). Остальное подгружать JOIN’ом или отдельным запросом при открытии заявки.
- Если нужен «снимок» на момент заявки — хранить один JSON (например, `property_snapshot TEXT`) вместо десятков колонок. Тогда схема не раздувается и изменения объекта не требуют миграций purchase_requests.

### 3.3 auction_winners.property_table

**Плюс:** В `auction_winners` уже есть `property_table` — это правильный подход. Имеет смысл использовать тот же подход в `bids` и при необходимости в других таблицах, ссылающихся на объекты.

## 4. Индексы

### 4.1 Уже есть

- По основным фильтрам индексы созданы: user_id, moderation_status, property_type, created_at по нужным таблицам, составные где нужно (user_id + moderation_status и т.д.).

### 4.2 Чего может не хватать

- **bids:** при добавлении `property_table` полезен составной индекс `(property_id, property_table)` для быстрой подгрузки объектов по списку ставок (если будете делать batch-запросы по паре (id, table)).
- **notifications:** если часто выбирают по `(user_id, is_read)` — составной индекс `(user_id, is_read)` ускорит выборку непрочитанных.
- **properties_apartments / properties_houses:** если часто фильтруют по `created_at` или по цене — рассмотреть индексы по `created_at`, `price` или составные под типичные запросы (например, moderation_status + created_at).

## 5. Стабильность и производительность

### 5.1 Уже сделано хорошо

- WAL, busy_timeout, foreign_keys, cache_size, temp_store — настроены в database.js.
- Retry при SQLITE_BUSY/SQLITE_LOCKED.
- Проверка целостности БД при старте и пересоздание при «malformed».

### 5.2 Рекомендации

- **Подготовленные запросы:** better-sqlite3 уже кэширует подготовленные запросы при повторных вызовах `db.prepare(...)`. Имеет смысл не создавать новые строки SQL в цикле, а использовать один подготовленный запрос с параметрами (что в основном уже так и есть).
- **Тяжёлые выборки:** для списков с пагинацией везде использовать LIMIT/OFFSET (или курсор по id), чтобы не тянуть тысячи строк за раз.
- **VACUUM/ANALYZE:** уже вызываются в `performMaintenance`. Имеет смысл вызывать их по расписанию (cron или по таймеру в непиковые часы), а не только при старте, если БД сильно растёт.
