# Проверки коммитов и переводов

GitHub Actions запускает `Translations`, `Tests`, `Build` и итоговый `Quality gate`
при каждом push, обновлении PR и в merge queue. Результаты видны у коммита,
в PR и во вкладке Actions. Незавершённые старые прогоны той же ветки отменяются
при новом push; последний коммит проверяется заново.

## Обязательная защита основной ветки

Одного workflow недостаточно: Actions запускается после приёма push и не отменяет
уже попавший в основную ветку коммит. Гарантия «ошибка не попадёт в основную ветку»
требует PR и обязательных проверок на стороне GitHub.

После первого запуска CI владелец или администратор репозитория должен открыть
[Settings → Rules → Rulesets](https://github.com/Andhanc/newsellyourbrick/settings/rules),
создать активный branch ruleset для `new-era` и включить:

1. **Require a pull request before merging**. Число обязательных одобрений можно
   оставить нулевым: отдельный ревьюер для прохождения тестов не нужен.
2. **Require status checks to pass** → **Quality gate**, источник GitHub Actions.
3. **Require branches to be up to date before merging**.
4. **Block force pushes** и запрет удаления ветки.
5. Пустой bypass list, чтобы правило действовало и для администраторов.

Остальные существующие правила следует сохранить. Не включайте ruleset до
появления проверок и исправления красных тестов. У текущего CLI-аккаунта
`vtichonenko-crypto` есть push-доступ, но нет административных прав: он не может
включить эту защиту. До её включения прямой push в `new-era` остаётся возможным.

Рабочий процесс: новая ветка → коммит → push → PR → зелёный `Quality gate` → merge.
При прямом push в основную ветку будут видны результаты тестов, но сломанный
коммит уже будет принят. Локальные Git hooks можно обойти, поэтому они не заменяют
защиту ветки. Если хостинг автоматически разворачивает каждый push, ожидание CI
для деплоя также настраивается отдельно в хостинге.

## Проверка локализации

```sh
npm ci
npm run test:i18n
npm run check:i18n
npm test
npm run build
git diff --check
```

`check:i18n` проверяет весь набор словарей, а новые ошибки в исходниках сравнивает
с `HEAD` (включая несохранённые в коммите новые файлы). Перед push нескольких
коммитов используйте `npm run check:i18n -- --base origin/new-era`.
В CI для PR используется общий предок с целевой веткой, для push — предыдущий
SHA. Для первой отправки новой ветки используется общий предок с основной веткой.
Ошибки выводятся с именем файла и строкой, в Actions также появляются аннотации.

Всегда проверяются:

- Наличие одинаковых ключей во всех языках `ru`, `en`, `de`, `es`, `fr`, `pl`, `sv`,
  включая вложенные объекты и элементы массивов.
- Строковые непустые значения и одинаковые параметры `{{count}}`, `{{price}}` и т. п.
  Шестнадцать существующих необязательных фрагментов заголовков онбординга могут
  оставаться пустыми; их список явно указан в проверке.
- Отсутствие повторяющихся JSON-ключей и точное совпадение web/legacy-словарей.
- Полнота небольшого нативного словаря `nativeStrings.ts` для всех семи языков.

Для исходников запрещается увеличение существующего долга локализации:

- Новые статические ключи в `t()`, `i18n.t()`, `nativeT()`, `i18nKey`, `titleKey`,
  `labelKey` и других перечисленных в проверке полях должны существовать.
  `defaultValue` не скрывает отсутствие ключа.
- Новый текст непосредственно в JSX, условных JSX-выражениях, пользовательских
  props (`placeholder`, `tooltip`, `aria-label` и т. п.), полях конфигурации
  (`title`, `label`, `message` и т. п.) и `showNotification()` требует перевода.
- Повторное добавление существующего непереведённого текста тоже является ошибкой.

Старые нарушения в исходниках не добавляются в редактируемый allowlist: сравнение
идёт с Git. `npm run check:i18n -- --strict` показывает весь долг, включая старый.
Словари при этом всегда проверяются полностью, без исключения старых ошибок.

Для нового блока используйте `t('newBlock_title')` и добавляйте перевод во все
семь web-словарей и их legacy-копии в том же коммите. Для данных, названий брендов
и других текстов, которые не переводятся, автоматическая проверка может требовать
обсуждения и уточнения правила вместо добавления фиктивного перевода.

Статический анализ не определяет язык и качество текста, не вычисляет произвольные
динамические ключи и не прослеживает все переменные до места отображения. Тексты
из API и серверных шаблонов им также не покрыты. Для новых динамических блоков
предпочитайте явную карту `titleKey`/`labelKey` и отдельный тест на все варианты.

## Существующие ограничения тестов

При первоначальном прогоне до настройки CI (2026-10-31, Node 26) получено:
874 теста, 841 прошёл, 31 упал, 2 пропущены. Среди причин — устаревшие проверки
русского текста прямо в компонентах, изменившиеся UI-контракты и импорт `vitest`
в `src/utils/ownerPropertiesList.test.js` при отсутствии этой зависимости.
CI запускается на Node 22; точные результаты нужно смотреть в соответствующем
прогоне Actions. Падения не скрываются и не помечаются успешными: `Tests` и
`Quality gate` останутся красными до исправления.

Два интеграционных теста development требуют `RUN_DEVELOPMENT_DB_TESTS=1` и
настроенной отдельной БД; обычный CI их пропускает по существующим условиям.
Заданный в workflow `DATABASE_URL` — фиктивный адрес для генерации Prisma,
рабочая БД и production-секреты тестам не передаются.

Продуктовые экраны не менялись. Сохраняются карусель стратегий, drawer и stories,
переход покупатель → продавец, общая галерея и access-gate, 3D-иконки риска,
ограничения инвестиций в аукционы и touch-вибрация сравнения. В переводах долей
для `de/es/fr/sv` восстановлены потерянные параметры `count` и `total`.
